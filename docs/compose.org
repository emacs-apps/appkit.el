#+title: Appkit compose
#+options: toc:2 num:nil

Appkit has no Draft model.  It gives a client's own editing buffer three small
guarantees: a semantic generation that tells edits from generated chrome, an
immutable capture of what was being edited, and one fenced asynchronous
operation (such as a send) at a time.

| Module                  | Use                                                        |
|-------------------------+------------------------------------------------------------|
| ~appkit-compose~        | the generic session, attached to any client major mode     |
| ~appkit-compose-edit~   | a temporary native-mode child editor for one string        |
| ~appkit-chat-compose~   | the multi-part chat composer for post threads              |
| ~appkit-markup-compose~ | codec selection and markup capture; see [[file:markup.org][markup]]             |

Appkit owns generations, captures, operation fencing, cancellation requests and
status presentation.  The client owns document meaning and validation, drafts
and persistence, autosave and close policy, attachments, transport, and every
outcome: accepted, rejected, unknown, saved or cancelled.

* Session

#+begin_src emacs-lisp
(appkit-compose-setup
 :snapshot-function #'example--snapshot          ; returns an owned client value
 :source-bounds-function #'example--source-bounds ; optional editable region
 :state-change-function #'example--state-changed  ; optional presentation hook
 :generation 0)
#+end_src

Setup does not change the major mode.  ~appkit-compose-session-mode~ installs the
change and kill hooks.  Disabling it or killing the buffer cancels the active
operation.

- An edit overlapping the source bounds advances ~appkit-compose-generation~
  once.  A semantic change outside the text, such as choosing an attachment or
  audience, calls ~appkit-compose-touch~ once.
- Generated chrome is written inside ~appkit-compose-without-tracking~.  That
  only suppresses generation changes; it does not make a real edit invisible.
- ~appkit-compose-reset~ loads another document: it cancels the active operation,
  replaces the generation and clears the modified flag.

~appkit-compose-capture~ returns ~(:generation N :value VALUE)~.  An operation
uses that capture as its only input; it never rebuilds its payload from the
live buffer after starting.  Appkit does not copy or inspect the value, so the
snapshot function must return owned data.

* Operations

#+begin_src emacs-lisp
(let ((owner (appkit-compose-operation-begin
              'submitting
              :generation (plist-get capture :generation)
              :label "Sending" :progress 0.0
              :cancel-function cancel)))
  ...
  (appkit-compose-operation-update owner :progress 0.5)
  ...
  (appkit-compose-operation-finish owner))
#+end_src

- Only one operation may be active; beginning another is a user error.
- Only the exact owner can update or finish it.  A stale owner is ignored.
- ~appkit-compose-cancel-operation~ records a request and calls the cancel
  handle or function once.  The operation stays current until the client
  settles it and calls ~appkit-compose-operation-finish~.
- Finishing clears presentation and retires the cancel handle.  It does not mean
  sent, saved or cancelled; that is the client's to record.

Status presentation is generic.  A /status field/ is a plist with ~:label~,
optional ~:value~ and an optional Appkit UI ~:action~, rendered by
~appkit-compose-status-fields-string~.  ~appkit-compose-status-text~ combines the
operation label with a percentage, and ~appkit-compose-progress-bar~ draws a bar.

* Child editor

~appkit-compose-edit-buffer~ edits one client string in a temporary buffer with a
native major mode, such as a code block:

#+begin_src emacs-lisp
(appkit-compose-edit-buffer
 owner initial-text
 :mode #'emacs-lisp-mode
 :buffer-name "*Example Code Block*"   ; content-free
 :validation-function #'example--check-code)
#+end_src

Finish keys (~C-c C-c~, ~C-x C-s~) and cancel keys (~C-c C-k~, ~C-c C-z~) are
layered over the mode's map.  It returns the accepted plain string, or nil after
cancellation.  The buffer is a lifecycle handle of OWNER (an App or Surface), so
stopping the owner cancels the edit, and the buffer is always killed before the
call returns.  The client chooses the mode and validation, and turns the string
into structured objects or wire format.

* Chat compose

~appkit-chat-compose-mode~ derives from ~appkit-chatbuf-mode~ and edits an
ordered sequence of items, such as the posts of a thread.  Committed items are
generated rows; the trailing composer edits one item at a time.  It is not a
universal document editor.

- An item is a plist with an internal ~:id~, optional ~:text~ and any client
  metadata (attachments, visibility).  An item with metadata and no text is
  kept, which allows attachment-only parts.
- ~appkit-chat-compose-items~ is the authoritative ordered snapshot.  Do not
  mirror it in another variable.
- ~appkit-chat-compose-set-items~ replaces the whole sequence without changing
  the generation or the active operation.  Use it to persist confirmed upload
  IDs or a published prefix mid-send.
- ~appkit-chat-compose-update-current-item~, ~-add-item~ and ~-drop-item~ each
  advance the generation once.  Moving between parts preserves the draft.
- Freeze editing with ~buffer-read-only~.  An active operation alone does not
  freeze it, and programmatic settlement of a frozen draft binds
  ~inhibit-read-only~ explicitly.

~appkit-chat-compose-setup~ takes callbacks for context text, status fields,
attachments or per-part lists, and the footer.  Pass ~:app~ to attach the
compose Surface to the client's App; without it the buffer runs as a
standalone Surface.  Stopping the Surface keeps the buffer and its draft.

Item bodies are plain strings: merging a part strips text properties, so
structured input objects do not survive into chat-compose items.  Clients that
need them in a single-part composer use ~appkit-chatbuf~ input directly (see
[[file:chat.org][chat]]).
